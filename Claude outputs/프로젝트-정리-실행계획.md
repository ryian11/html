## 4. project_rules.json 최종 스키마 — `docs/SCHEMA.md` 확정 내용

> 아래가 실제로 `docs/SCHEMA.md`에 들어갈 내용이다. `project_rules.json-스키마-확정안.md`(9장·A~F)를
> 참조 문서용 서술에서 **규정 문서용으로 압축**했다 — "왜 이렇게 정했는가"의 근거·예시는 archive의
> 원본 문서에 남기고, 여기는 "지금 규칙이 무엇인가"만 남긴다.

### 역할 분리 (가장 중요한 한 문장)

> **`project_rules.json` = 이 프로젝트의 구조·경로·단원·prototype 정보. 프로젝트마다 1개, Claude(또는 사람)가 분석해서 만든다.**
> **`rules/<recipe>/rules.json` = 이 recipe가 HTML을 만드는 방법. recipe마다 1개, 여러 프로젝트가 재사용한다.**

### `project_rules.json` 구조

```
project    { id, name, recipe }
paths      { storyboardDir, soundXlsx, contentsDir, guideDir }   ← root 기준 상대경로
units[]    [{ id, name, storyboard, ops, sheet, guide?, kr? }]
prototype  { units: [{ id, pages }] }                             ← name/type 등 중복 저장 안 함(units[]/proto_scan이 대신 제공)
patterns   { pageFilename, mp3Prefix, storyboardSheets:{syntax,miniVocab,dictation} }   ← 확인된 런타임 값
discovery  { storyboardFilename?, specialUnitFilename?, contentsFolder?,
             soundSheetGuess?, guidePdfGuess? }                   ← 최초 탐색 보조, 전부 선택, 없어도 정상 동작
```

`patterns` vs `discovery`: **없으면 시스템이 못 도는 값 = patterns / 없어도 units[]를 다 적으면 그만인 추측 = discovery.** (검증 완료 — 스키마 확정안 2장)

### `rules/<recipe>/rules.json` 이 담는 것 (project_rules.json엔 절대 안 넣음)

```
popup.*                버튼 번호 등 HTML 조립 규칙
skeleton.*              페이지 css/js 조립 뼈대
assets.*                배경/제목 이미지 파일명 규칙
sound.col.* / idPattern / mp3.{sep,case}    엑셀 열 위치·ID 패턴·mp3 이름 변환 규칙(recipe 공통 처리 방식)
measure.*                여백 등 측정 규칙
```

### 지금 project_rules.json에서 제거해야 하는 것 (코드 단계에서 실행)

| 값 | 있던 곳 | 이유 | 옮길 곳 |
|---|---|---|---|
| `project.root` | project_rules.json | settings.json과 이미 어긋나 있고 아무도 안 읽음 | settings.json이 기준 |
| `paths.wordDicDir` | project_rules.json | 읽는 코드 없음(완전한 죽은 값) | 제거 |
| `storyboard.sheet.Dictation`/`.구문 해설`/`.미니 단어장`/`.Lesson 3_전자저작물용 지시문 모음` | rules.json | 코드가 찾는 키(`storyboard.sheet.syntax` 등)와 이름이 달라 영원히 안 먹음 | `patterns.storyboardSheets.*` |
| `sound.sheet` (`%d과`) | rules.json | `patterns`(현 `discovery.soundSheetGuess`)와 중복 | 제거(project_rules.json 쪽이 기준) |

### 새 프로젝트 검증 결과 (재확인 완료)

숫자 아닌 단원 ID(UnitA 등) — 통과 / 다른 폴더 구조 — 통과(전부 상대경로) / 다른 엑셀 시트명 — 통과 / **다른 mp3 파일명 규칙 — "접두사 차이"까지만 통과, 조립 순서 자체가 다른 경우는 recipe 쪽(rules.json) 템플릿화가 별도 필요(미해결로 정직하게 남김)**.

```gitignore
# 다만 지금 방식대로 계속 git으로 이력 관리를 원하면 이 줄은 빼고 유지)
# _backup/measure/
# _backup/layout/
# _backup/산출물/

# 판단 필요 — 생성 결과물 (다시 만들 수 있지만, 지금 git diff로 결과 변화를 확인하는 용도로
# 쓰고 있을 수 있어 임의로 제외하지 않음. 이 프로젝트의 실제 작업 습관에 달려 있어 사용자 확인 필요)
# 단원자료/data*.py
# 단원자료/{scrolls,popscroll,krlayout}*.py
```

**"확실" 항목만 먼저 넣고, "판단 필요" 두 묶음은 사용자 확인 후 넣는 것을 권장한다** — 지금 git으로 결과물 변화를 diff해서 확인하는 습관이 있다면 gitignore에 넣으면 안 되기 때문이다(이건 코드가 판단할 수 없는 부분이라 추측하지 않는다).

**중요**: `.gitignore`를 추가해도 **이미 추적 중인 파일은 자동으로 빠지지 않는다.** `git rm --cached -r <경로>`를 함께 실행해야 실제로 추적이 풀린다 — 이것도 "다음 실제 수정 작업"에 포함해야 한다.

## 8. 이름 변경 후보 — CJ 종속 vs 일반 생성기 관점 구분

### ① CJ 프로젝트 자체에 종속된 이름(일반화하려면 반드시 짚어야 함)

| 이름 | 문제 | 제안 |
|---|---|---|
| 최상위 폴더 `_딕테이션_생성기` | 실제 코드는 Reading 생성이 메인이고 딕테이션은 `_옛도구/`로 완전히 분리돼 있음 — 이 도구의 **출발점 흔적**이지 지금 역할과 안 맞음 | `_HTML생성기` 또는 `_교재생성기`(런처 `HTML생성기.vbs`, 화면 제목과 일치). ⚠️ `read_paths.py:21`에 폴더명이 하드코딩돼 있어 함께 고쳐야 함 |

### ② CJ 종속은 아니지만 일반 생성기 코드로서 이름이 실제 역할과 안 맞는 것

| 이름 | 문제 | 제안 |
|---|---|---|
| `project.json` / `project_rules.json` / `rules/cj_reading/rules.json` | 셋 다 "프로젝트"·"규칙"만 써서 이름으로 구분 불가 | `project_rules.json` → `project_structure.json`, `rules.json` → `html_rules.json`(recipe 쪽), `project.json`은 병합 후 제거 |
| `read_paths.py` | "읽는다"로 읽히지만 실제론 경로 상수 레지스터 | `paths_registry.py` |
| `read_import.py` / `read_gen.py` | 레시피 단계명(`extract`/`build`)과 파일명이 안 맞음 | `reading_extract.py` / `reading_build.py` |
| `discover()` | "구조를 결정하는 주체"로 읽히지만 실제론 "빈 자리만 채우는 보조"(지침 9번과 이름이 정면 충돌) | `probe_units()` / `scan_for_new_units()` |
| `recipe` / `recipes/` | "한 번 쓰는 지시서"로 읽히지만 실제론 수명이 긴 **교재별 어댑터 모듈** | 이름 변경 비용이 커서(`/api/recipes` 등 화면 전반에 박힘) 이름보다 `docs/PROJECT.md`에 정의 한 줄 추가를 권장 |
| `GET/POST /api/project` | 실제로는 `project.json`이 아니라 `project_rules.json`을 다룸(이름-실체 불일치) | `/api/units` 또는 `/api/structure` |
| `read_run.py` | 이름만 보면 "표준 실행 진입점"인데 실제론 JSON을 우회하는 옛 CLI | 삭제 확정(5장) |

우선순위: **`project.json`/`project_rules.json`/`rules.json` 3파일명이 가장 심각**(매일 보는 이름인데 구분이 안 됨). 나머지는 6장(project_rules.json 코드 반영) 작업과 묶어서 한 번에 처리하는 것이 효율적이다(같은 파일들을 두 번 안 건드림).

## 9. 향후 AI/API 구조 (지금 구현 안 함 — 역할만 정리)

```
자료 분석 단계 (프로젝트당 1회, 아래 중 하나 선택)
      ↓
project_rules.json
      ↓
일반 HTML 생성기 (지금처럼 순수 Python — 이 선택과 무관하게 항상 동일)
      ↓
HTML 생성
```

| 방식 | 역할 |
|---|---|
| **Claude API** | 폴더 목록·시트명·파일명을 넘겨 `project_rules.json` 초안을 자동 생성. 스키마(4장)가 이미 문서화돼 있어 프롬프트로 바로 활용 가능. 사람이 검토·확정하는 절차는 지금과 동일하게 유지 |
| **OpenAI API 등 다른 LLM** | 위와 같은 역할. 코드 어디에도 특정 벤더 종속이 없어(런타임 확인 완료, 6장 근거) 모델만 바꾸면 됨 |
| **사내 AI 서버 / 로컬 LLM** | 같은 역할을 인터넷 없이 수행. 경로·시트명 후보 추리기 같은 정형 작업엔 적합, PDF 좌표 판단처럼 시각적 요소가 있는 곳은 사람 검토 비중이 커질 수 있음 |
| **사람이 직접 작성** | SCHEMA.md만 보고 손으로 JSON을 채움 — AI 없이도 지금 이미 가능한 경로 |

**공통 사실(재확인)**: 런타임 파이프라인 전체를 다시 grep해도 API 호출 코드가 0건이다 — 위 네 방식 중 무엇을 고르든 "일반 HTML 생성기" 쪽 코드는 **한 글자도 안 바뀐다.** 어떤 방식을 쓸지는 지금 결정할 필요 없고, 실제 두 번째 프로젝트를 받을 때 정해도 늦지 않다.
