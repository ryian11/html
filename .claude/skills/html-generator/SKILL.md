# HTML 생성기 프로젝트 Skill

## 작업 시작 전 반드시 읽을 문서

이 프로젝트에서 작업하기 전에 아래 4개 문서를 먼저 읽는다.

1. `docs/PROJECT.md`
2. `docs/RULES.md`
3. `docs/PROGRESS.md`
4. `docs/ISSUES.md`

이 4개 문서는 프로젝트의 목적, 현재 구조, 생성 규칙, 진행 상황, 알려진 문제를 설명한다.  
SKILL.md에는 작업 원칙과 절차만 두고, 프로젝트의 세부 지식은 위 문서에 둔다.

## 프로젝트의 핵심 목표

이 프로그램은 특정 프로젝트의 폴더 구조를 코드에 고정하는 프로그램이 아니다.

목표 구조는 다음과 같다.

프로젝트 자료
→ Claude가 프로젝트 구조/규칙을 최초 분석
→ 프로젝트 정보를 구조화된 JSON으로 저장
→ 일반 HTML 생성기가 JSON을 읽음
→ HTML 생성

Claude가 프로젝트별 정보를 최초 분석한 뒤에는 일반적인 HTML 생성 과정에서 Claude를 계속 사용할 필요가 없어야 한다.

## 가장 중요한 원칙

### 1. 프로젝트별 정보를 Python 코드에 하드코딩하지 않는다

다음과 같은 정보가 특정 프로젝트에 맞춰 코드에 직접 들어가면 안 된다.

- 프로젝트 루트 경로
- 스토리보드 폴더명
- 스토리보드 파일명
- Excel 파일명
- Excel 시트명
- PDF 경로
- 이미지 경로
- 오디오 경로
- 콘텐츠/출력 경로
- 단원 목록
- 단원별 경로
- 프로토타입 단원
- 프로토타입 페이지 파일명
- 페이지 파일명 규칙
- 특정 프로젝트의 특수 단원 구조

현재 코드에 이런 하드코딩이 남아 있다면 새로운 프로젝트에서도 동작할 수 있도록 구조를 분리하는 것이 장기 목표다.

### 2. 현재 프로젝트의 구조를 보편적인 규칙이라고 가정하지 않는다

예를 들어 다음과 같은 현재 프로젝트의 구조를 다른 프로젝트에도 자동으로 적용한다고 가정하지 않는다.

- `01_스토리보드`
- `02_사운드`
- `Lesson 01.xlsx`
- `lesson01`
- `p152_03.html`

이것들은 현재 프로젝트에서 발견된 실제 사례일 뿐, 새로운 프로젝트의 보편적인 규칙이 아닐 수 있다.

### 3. JSON을 프로젝트 구조의 기준으로 사용한다

Claude가 프로젝트를 분석할 때 발견한 프로젝트별 정보는 구조화된 JSON에 기록하는 방향으로 설계한다.

JSON에는 필요에 따라 다음 정보가 포함될 수 있다.

- 프로젝트 루트
- 자료 경로
- 스토리보드 경로/파일
- Excel 경로/시트
- 녹음 대본
- 가이드/PDF
- 이미지
- 오디오
- 콘텐츠
- 출력 경로
- 단원 목록
- 단원별 경로
- 단원별 자료 연결
- 프로토타입 단원
- 프로토타입 페이지
- 페이지 목록/순서/종류
- 페이지와 스토리보드/Excel/이미지/오디오의 관계
- HTML/CSS/JS 규칙
- popup 규칙
- 특수 단원 규칙
- 예외 사항

실제 JSON 스키마는 코드를 충분히 조사한 뒤 결정한다. 임의로 단순화하지 않는다.

### 4. JSON에 없는 정보를 임의로 추측하지 않는다

생성에 필요한 정보가 JSON에 없다면 다음 중 하나를 수행한다.

- 명확한 오류/경고를 표시한다.
- 분석 단계에서 해당 정보를 추가하도록 한다.

현재 프로젝트의 폴더 구조를 보고 조용히 추측하여 새로운 프로젝트에도 적용하는 방식은 피한다.

### 5. 기존 기능을 함부로 제거하지 않는다

구조를 일반화하는 과정에서 현재 정상적으로 동작하는 기능을 이유 없이 삭제하거나 변경하지 않는다.

특히 다음을 확인한다.

- 기존 생성 결과
- 페이지 선택 생성
- 프로토타입 분석
- 미리보기
- 백업/되돌리기
- rules.json을 사용하는 기존 규칙
- 특수 단원 처리
- 회귀 비교

변경 전 기존 동작과 변경 후 동작을 비교한다.

## 작업 절차

작업 요청을 받으면 다음 순서를 따른다.

### 1단계: 문서 확인

먼저 다음 문서를 읽는다.

`docs/PROJECT.md`
`docs/RULES.md`
`docs/PROGRESS.md`
`docs/ISSUES.md`

### 2단계: 현재 코드 구조 확인

관련 코드를 실제로 확인한다.

특히 다음을 확인한다.

- 데이터가 어디서 읽히는지
- 어떤 함수가 프로젝트 구조를 찾는지
- 어떤 데이터가 UI로 전달되는지
- 단원 목록이 어떻게 만들어지는지
- 페이지 목록이 어떻게 만들어지는지
- HTML 생성에 어떤 데이터가 사용되는지
- 현재 프로젝트 정보가 어디에 하드코딩되어 있는지
- project.json / rules.json / 기타 JSON의 역할

### 3단계: 데이터 흐름을 먼저 설명

코드를 바로 수정하기 전에 필요하다면 다음 흐름을 먼저 정리한다.

자료
→ 분석
→ JSON
→ UI 선택
→ 생성 데이터
→ HTML

특히 사용자가 현재 프로그램의 동작 원리를 이해하려는 경우에는 코드 수정보다 구조 설명을 우선한다.

### 4단계: 프로젝트별 정보와 공통 로직을 구분

각 정보를 다음처럼 구분한다.

- 프로젝트마다 달라지는 정보 → JSON/프로젝트 데이터
- 모든 프로젝트에서 공통인 생성 로직 → 프로그램 코드
- 프로젝트 분석을 통해 발견해야 하는 규칙 → 분석 결과 JSON
- 단순 검증/진단 기능 → discover 등의 보조 기능

### 5단계: 수정 계획 제시

수정이 필요한 경우 먼저 다음을 명확하게 한다.

- 현재 문제
- 원인
- 어느 파일을 수정하는지
- 프로젝트별 정보인지 공통 로직인지
- 새로운 프로젝트에서도 동작하는 이유
- 기존 기능에 미치는 영향
- 테스트 방법

### 6단계: 사용자가 수정 요청을 한 경우에만 코드 수정

사용자가 분석/설명을 요청한 경우에는 코드를 임의로 수정하지 않는다.

수정을 요청한 경우에도 가능한 한 작은 범위로 변경하고 기존 기능을 보존한다.

### 7단계: 테스트

수정 후에는 가능한 범위에서 실제 코드/구조를 확인하고 테스트한다.

특히 일반화 작업에서는 현재 프로젝트 하나만 맞는 것이 아니라 새로운 프로젝트에서도 프로젝트별 JSON만 바꾸면 동작할 수 있는지를 확인한다.

## 현재 프로젝트에서 특히 주의할 부분

현재 코드에는 과거 프로젝트에서 사용하던 구조가 남아 있을 수 있다.

예를 들어:

- `read_paths.py`
- `cj_reading.py`
- `proto_scan.py`
- `read_gen.py`
- `project.json`
- `rules.json`

등을 조사할 때 특정 값이 어디에서 오는지 확인한다.

단순히 하드코딩된 값을 다른 JSON으로 옮기는 것만으로 일반화가 완료되었다고 판단하지 않는다.

중요한 것은:

> 프로젝트별 지식은 프로젝트 데이터로 분리하고, 프로그램은 그 데이터를 읽어 동작해야 한다.

## discover()의 역할

`discover()` 같은 자동 탐색 기능은 유지할 수 있다.

다만 최종적으로 프로젝트 구조의 기준이 되는 정보와 자동 탐색 결과를 구분한다.

목표는:

- Claude 분석 결과 JSON → 프로젝트 구조의 기준
- discover() → 검증/진단/보조 기능

이다.

discover()가 현재 프로젝트 폴더 구조를 보고 새로운 프로젝트의 규칙을 임의로 결정하는 구조가 되지 않도록 한다.

## 변경 판단 기준

새로운 코드를 추가하거나 기존 코드를 수정할 때 항상 다음 질문을 한다.

> 이 코드는 모든 프로젝트에 공통인 로직인가, 아니면 현재 프로젝트에서만 필요한 지식인가?

현재 프로젝트에서만 필요한 지식이라면 코드에 넣기 전에 JSON으로 분리할 수 있는지 검토한다.

## 최종 목표

새로운 프로젝트가 들어왔을 때 다음과 같은 과정이 가능해야 한다.

1. 프로젝트 자료를 준비한다.
2. Claude가 프로젝트 구조와 규칙을 분석한다.
3. 분석 결과를 프로젝트 JSON으로 저장한다.
4. 일반 HTML 생성기를 실행한다.
5. 해당 JSON을 선택한다.
6. 프로토타입 단원을 선택한다.
7. 생성할 단원을 선택한다.
8. 필요한 페이지를 선택한다.
9. HTML을 생성한다.

그리고 새로운 프로젝트가 추가될 때마다 Python 코드에 프로젝트별 경로와 규칙을 새로 작성하지 않는 것을 목표로 한다.
